# Agent Vision Phase 2 — Recorder and Session Inspector

## Contract and scope
Recorder is application-layer exploration memory, not a macro, workflow builder, or workflow runtime. The shared Recorder.execute boundary surrounds CLI/MCP application dispatch, including argument conversion and operation errors. PlatformService and OpenCV Core are unchanged. Existing 13 Vision tools and their unbound calls remain compatible. Recording is explicit per operation: CLI global --session or VISION_SESSION_ID, MCP session_id. No ambient global active session. Session ID is correlation, not authentication. A valid active session is required for bound operations; unknown/paused/stopped sessions reject rather than act silently.

## Persistence and sequencing
Workspace is the canonical FrameStore directory. SQLite recorder.sqlite stores sessions (ID, name, goal, device, workspace, timestamps, status), events (ID, session ID, sequence, start/end timestamps, operation, device, inputs, structured result, status, error, evidence), and annotations (ID, event ID, session ID, timestamp, kind, semantic payload). Status: active -> paused -> active; active/paused -> stopped, terminal. SQLite transaction allocates sequence and commits pending receipt before invocation. No automatic replay. Pending means outcome unknown after interruption; inspect fresh state. Cross-process workspace lock serializes application adapter operations and lifecycle transitions, including unbound operations touching existing JSON stores. Direct Python clients bypassing the adapter must coordinate separately. Different sessions can share a device but do not imply exclusive device ownership. Explicit device/frame/ref/asset-source mismatch is rejected before device action.

## Operation and evidence
Supported: snapshot, crop, resize, assets_register, find, click, swipe, type, key, wait. Each bound call creates one event. Success means application execution completed, not semantic task success; failed and timeout retain error information. No-match is a successful query with found=false. Device action receipts preserve verified=false; wait verification refers only to the specified visual condition. Invalid CLI syntax rejected before dispatch is not an operation receipt. Unknown session has no valid log destination. Recorder never manufactures before/after frames: evidence refers only to existing source/input frames and actual returned frames, assets and references. Input frames pinned before use; new frames protected at save before TTL/capacity cleanup. Protected frames are outside the transient cache budget. Asset revisions retained by SHA-256 hardlink to existing PNG (copy fallback); same-name overwrite cannot destroy the prior revision. Ref IDs link existing scoped reference metadata. Retention indefinite in Phase 2; no automated deletion or retention policy. No binary/base64 copied into event rows.

## Privacy and limits
Type input and errors always masked, including CLI diagnostics. Common secret keys omitted/redacted; strings and large lists bounded (4000 characters, 100 items); recorded CLI find max_results <=100. Do not include secrets in session goals or free-form annotations; screenshots can contain sensitive content and are not automatically redacted. Annotation maximum 8000 serialized characters. UTF-8 MCP stdio on Windows; CLI JSON uses ASCII escapes losslessly. Local files are not encrypted at rest.

## Inspector
List, status, inspect/summary, events, event, history, annotations, latest-checkpoint, resume-context. Event pages ascending sequence cursor; filter operation/status; limit 1..50, next_cursor null when exhausted. List and annotation pages use row cursor. Event detail includes original structured metadata subject to redaction/truncation; event list omits verbose result and input. History includes evidence links. Resume context provides session goal/status, latest checkpoint with its event evidence, latest explicit PASS annotation, recent events/annotations/non-success, recent distinct asset revisions with provenance and pagination indication. Completed steps, state, issues and next action derive from explicit LLM annotations/checkpoints, not inferred from execution. Annotation fields: purpose, state, expected_postcondition, observation, verification (PASS/FAIL/UNKNOWN), failure_reason, insight, next_step, completed_steps, unresolved_issues. Each annotation/checkpoint requires an event belonging to the session. Checkpoint is a distinct kind; annotations remain append-only, including corrections.

## Interface
CLI: vision --store-dir STORE record start --name NAME --goal GOAL --device SERIAL; vision --store-dir STORE --session SID snapshot --device SERIAL --json. Lifecycle/query: vision record ACTION --session SID; event/annotate/checkpoint require --event EID, annotation/checkpoint require --annotation JSON; events supports --limit/--after/--operation/--status; annotations supports --kind. Start/list don't require SID. Same store across processes.
MCP: vision_record_start, list, status, pause, resume, stop, inspect, summary, events, event, annotate, checkpoint, annotations, history, resume_context, latest_checkpoint. All except start/list require session_id. Annotation/checkpoint require event_id and annotation object. Existing Vision tools gain optional session_id for recorded operations. No Orca DAG or new toolchain.

## Non-goals
Workflow generation, runtime, recovery learning, unattended game agent, new OCR, dashboard, browser, Orca orchestration, agent-specific Core changes.
